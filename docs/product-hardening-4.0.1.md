# Qiaomu Book Reader 4.0.1 产品健壮性审计

状态：功能分支候选版已在真实 Obsidian 中回归；用户已授权通过 PR 合并 main。本文保留分轮验收证据，最新结果见 [交互优化清单](interaction-polish-4.0.1.md)，是否已合并以 PR 为准，不代表 GitHub Release 已发布。

## 设计基线

本轮使用 `qiaomu-design` 的产品打磨流程，主要参考 Notion 的内容优先层级和 Claude 的温和编辑感：细边框、低饱和背景、受克制的阴影，不用重气泡和大面积品牌色。阅读内容始终是主角，AI 和恢复提示只在需要时出现。

## P0 修复

| 问题 | 风险 | 处理 |
| --- | --- | --- |
| 扫描 PDF 切到 EPUB/文字 PDF 后，AI 仍保留“无文字层”状态 | 对话上下文错书 | AI 侧栏绑定活动 ReaderView；跨书时清掉旧文本，EPUB 不再因当前是封面而被当成扫描文档 |
| 连续快速打开图书 | 旧的异步结果覆盖新书 | 新增 AbortController 加载代次，只最新任务允许提交 UI，关闭时释放 PDF 加载任务 |
| 大 PDF 或侧栏变宽时显示空白页 | 用户认为文档损坏或插件卡死 | 保留加载幕直到布局完成，先给 Chromium 一次绘制机会；检测“总页数很多但所有正文都映射到第 1 页”时自动重排一次 |
| CLI 已登录仍报“请检查登录” | 可用的 AI 被错误禁用 | 不再使用可产生假阴性的状态命令做硬门禁；点击确定后真实建立 ACP 会话并发送最小生成请求，成功才自动启用 |

## 高价值 P1

| 问题 | 处理 |
| --- | --- |
| 清空对话记录使用系统 `confirm` 且范围不明 | 改用 Obsidian 确认弹窗，明确分为“清空本书”和“清空全部” |
| `reading-progress.json` 为空文件或损坏时容易被后续覆盖 | 停止写入该存储，设置页持续显示文件路径、救援备份路径、“在文件列表中显示”和“重新检测” |

| lint 噪声掩盖真实问题 | 仅对明确的产品专名加白名单，`npx eslint src/` 回到 0 警告 |

## 第二轮：对话输入与恢复

- 桌面与移动端复用输入控制器：中文输入法确认候选词不误发送；生成期间按 Enter 不清空追问草稿；上次请求失败不覆盖新输入。切换上下文恢复草稿后同步更新发送按钮和输入框高度。
- 停止、超时或 ACP 断开时保留已生成的 Markdown，标记回答未完成，并保留来源、复制、保存和重新生成入口；历史记录保留中断标记。
- 所有历史回答均可复制、保存；只有最新回答允许重新生成，过期按钮不能误操作后来问题。操作按钮不再依赖鼠标悬停显示，触屏热区至少 44px。
- 向上阅读时不被最终回复拉回底部；可点击“回到最新回复”恢复跟随。
- 故障恢复通过真实对话控制器的 DOM 测试注入取消、超时和 ACP 断开验证；并非在 Obsidian 中实际切断网络。

既有能力回归（不是本轮新增）：4.0.0 已有独立 AI 回答笔记路径，以回答为正文；PDF 每本书一篇阅读笔记，文字 PDF 支持全文或选文上下文，扫描 PDF 保留原页阅读和本书笔记。

## 第三轮：阅读进度恢复与防丢失

- 进度保存前，先在插件目录写入并读回校验独立的 `reading-progress-recovery.json`，随后通过 Obsidian 的 `DataAdapter.process` 更新已有主文件，并再次读回校验。恢复副本失败时不触碰主文件。
- 即使主文件因空内容或损坏而暂停写入，新的阅读位置也继续保存至独立副本；重启时仅加载源路径匹配的副本，保留主文件的保护状态，不静默覆盖异常原件。
- 保存过程中发现主文件变为无效 JSON 时停止覆盖；无法读取和一般写入失败使用不同提示，不再一律要求检查权限。
- 用户恢复主文件并点击“重新检测”时，按 `lastRead` 合并较新的内存位置，保留段落锚点，并验证重新保存成功后才报告恢复。
- 新增 9 项测试覆盖恢复副本写入失败、截断写入、同步破坏、重启回退、来源隔离、较新位置合并和恢复后的保存失败。这里的故障通过模拟存储注入，不在用户真实文件上破坏性测试。
- 该保护降低写入中断和同步异常带来的丢失风险，不能保证外部同步服务、多个设备同时写入或磁盘故障永不损坏数据；仍需保留同步版本历史与独立备份。
- 经用户授权，本地异常进度文件已保留副本，从有效备份与较新记录恢复 6 本书，并保留当前书的内存段落锚点。真实翻页后主文件与独立恢复副本的 6 本书记录一致；重载后可恢复正文位置，无保存失败提示。页码会随排版变化，持久化定位以段落锚点为准。

## 性能与 CLI 证据

- PDF.js 文字提取：扫描样本 248 页在 73ms 完成，0 字符；报告样本 32 页在 291ms 完成，41,812 字符。首屏的主要耗时是 Chromium 固定排版，当前通过持续加载反馈与崩塌自检消除“无反应空白”。
- 真实 CLI 最小生成：Grok 首 token 15.324s / 总计 15.736s；Kimi 首 token 6.750s / 总计 6.824s。这说明 Grok 的慢主要在首次推理/连接，而不是 Markdown 渲染。
- ACP 初始化：Grok 7.866s，Kimi 1.675s，Codex 1.183s，Claude 0.802s，ZCode 2.177s；五个 provider 均成功建立会话。Grok 的 `models` 状态命令在同一台机器上误报未认证，而 `agent stdio` 真实生成成功，因此不再用前者做硬门禁。
